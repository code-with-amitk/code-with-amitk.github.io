Transaction?

A transaction is a way for an application to group several reads or writes(INSERT INTO, SELECT x FROM) together into 1 logical unit.
Its upto Application to decide whether it wants every read/write to be written directly into DB or group several statements as 1 transaction 
Application --INSERT INTO--> |DB Manager| --> | DB |

Modes of Transactions

AutoCommit (Default Mode) Explicit Mode
What Every INSERT is a seperate transaction

Application does not call any dbmgr API, its default mode. Every read/write is a seperate transaction
That means every insert is directly written into DB
When you connect to the database and execute an INSERT command, the driver immediately sends a hidden BEGIN before the command and a hidden COMMIT immediately after it finishes. Every single command you run is its own, isolated, permanent transaction

Application sends db.begin_transaction() marking start of transaction
Application sends multiple data packets (e.g., INSERT, UPDATE, DELETE statements). The DBMgr writes these changes to a Temporary log (Write-Ahead Log)
Application sends a db.commit() instructing DBMgr to write into DB
Error: Application sends db.roll_back() to discard all changes. Once the database Rollback, it deletes entry from Temporary(WAL log)

Terms

Read Related

Term Description
Dirty Read A transaction is writing some row to the database, but the transaction got aborted inbetween, ie data is not committed.
if another transaction can see that uncommitted data, it is a dirty read
To Prevent Dirty Read? Database remembers both the old committed value and the new value set by the transaction. Currently ongoing write transaction holds the write lock. While the transaction is ongoing, any other transactions that read the object are simply given the old value. Only when the new value is committed do transactions switch over to reading the new value.
Read Skew / Non repeatable read Say Alice has $1,000 of savings at a bank, split across two accounts with $500 each. Now a transaction transfers $100 from one of her accounts to the other. If she looks at balance at same moment she might find 500$ in one, 400$ in another
Solution: Snapshot Isolation

Write Related

Term Decription
Dirty Write Two transactions concurrently try to update the same row in a database. 1st write transaction was uncommitted, data in DB is in inconsistent state
On top of this incorrect data, 2nd transaction writes, this is Dirty write.
To prevent dirty write? Take lock over row then write a transaction, if transaction fails revert the change and then release the lock
Write Skew / Phantom Race condition caused when 2 transactions update different rows in same table after reading common data from table

Distributed Transaction

What: A database operation that updates data across 2 or more network seperated databases
Features of Distributed Transaction
  1. All Commit or All Abort: Either all nodes commit or all nodes abort.
  2. ACID: Distributed transaction should follow ACID

Methods to Achieve Distributed Transactions

1. Two Phase Commit (2PC) (Also called XA Transaction)

External transaction coordinator (e.g., Zookeeper) manages the commit process across multiple databases.
This is 1 of method of Consensus

Consider a Example of a pizza ordering system:
  Where the order service acts as the coordinator, which generates a globally unique transaction ID
  kitchen service and transaction service are participants.

    Note over TxSvc: Lock Released
    TxSvc-->>OrderSvc: Done
Steps
1. Coordinator generates globally unique transactionId and sends to microservices. Now-on-wards microservices will use same id for communication.
2. Coordinator sends Prepare message(with transactionId) asking microservices whether they can commit or not?
3. When microservices recieves prepare, it makes sure that it can commit to DB at any cost.
- Even if microservices crashes After sending Yes. Then after recovery it has to commit the transaction.
- There is no turning Back.
5. Coordinator recieves response from all nodes. This is called COMMIT POINT
6. Coordinator writes its decision to Transaction log. so that if any microervice responds with No, whole commit can be moved to prev state.
7. Phase-2: Coordinator Send Message to commit. microervice Commit ie write to DB else //if any one says no Phase-2: Send Abort Message to all microervice via coordinator

DOUBT/UNCETAIN STATE:
- Coordinator sends prepare, microervice voted Yes, and Coordinator crashes.
Now microervices are in Doubt state. microervices will wait forever for Coordinator to send Phase-2 message(Commit or Abort).

HEURISTICS DECISIONS:
Microervices can communicate & decide amongst themseleves once did not hear from Coordinator for particular time.

Problems with 2PC

1. Not supported by modern technologies Eg: NoSQL DB does not support. Apache Kafka, Cassandra, RabbitMQ does not support.
2. 2PC is form of Synchronous RPC: Kitchen microservice is waiting, holding locks If coordinator crashes → Kitchen blocks indefinitely and even cannot write other transactions
  Solution: Saga Design Pattern

2. Saga Design Pattern

Dictionary Meaning of Saga:
  A long, epic story or narrative detailing a series of adventures, events, and twists over time. Just like an epic story has multiple chapters that unfold sequentially—where a plot twist or failure in chapter three might force the characters to backtrack or undo what they did in chapter one
  Saga design pattern is carried over multiple microservices, where each microservice does its own local DB transaction, listen on message & also compensate or revert the DB write if something goes wrong.

Where Saga can be used?
1. Distributed database updates(ie Distributed Transactions)
2. Anywhere in long-running business process or workflow that spans multiple isolated systems that cannot use standard ACID transactions.
Examples:
  E-Commerce Checkout & Fulfillment: Many microsservices, many databases
  Travel Booking: Flight, Hotel, Car Rental all are separate systems
  Loan Application: Credit Check, Risk Assessment, Document Verification. All are separate systems

Concept of Saga
- A Saga is an architectural pattern for managing distributed transactions across multiple independent microservices without locking data globally.
- Microservice 1 performs a DB/Shard write to its database and publishes an event to Kafka, Microservice 2 consume this event to execute the next local write(on its DB).
- If any step down the line fails, the saga sequentially triggers compensating transactions (undo actions) via event messages to maintain eventual consistency across the system.

(Steps 1–4)
  Rather than consulting a central coordinator, the Recvr Pod independently computes the destination shard using local CPU memory (hash(userId) % num of Shards).
  This eliminates network bottlenecks and allows any stateless pod to process the incoming request identically without external lookups.
(Steps 5–6)
  The pod directly writes the tweet to Shard1 (Shard_01) and receives an acknowledgment
(Steps 7–8)
  Instead of Pod publishes a TweetCreated event to Kafka and immediately returns a 200 OK response to the client.
(Steps 9–11)
  Consumer Pod picks up the event from Kafka to execute the next phase of the workflow.   It determines the target shard (either via local hash calculation or by reading metadata directly from the event payload) and writes the data to the Downstream Timeline Shard (Shard_02).
